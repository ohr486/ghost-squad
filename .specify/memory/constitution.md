# Ghost-Squad プロジェクト憲章

## コア原則

### I. マルチエージェントアーキテクチャ

Ghost-Squadシステムは、明確な責任を持つ協調型AIエージェントを中心に機能を構成しなければならない。すべてのミッション処理は、明確なエージェントノード（planner → worker → reporter）を持つLangGraphベースの「ghost_brain」ワークフローを通過する必要がある。

**遵守必須ルール**:
- すべてのミッションは完全なエージェントワークフローを通過しなければならない
- エージェントノードは単一の明確に定義された責任を持たなければならない
- エージェントの状態はAgentStateを介して明示的に定義・共有されなければならない
- LLM呼び出しにはエラー耐性のためのフォールバックシミュレーションを含めなければならない

**根拠**: マルチエージェントアーキテクチャは、攻殻機動隊にインスパイアされた「Living Kanban」コンセプトの中核である。協調エージェントにより、Ghost-Squadを従来のカンバンツールと差別化するインテリジェントなタスク分解と実行追跡が可能になる。

### II. テストファースト開発（遵守必須）

すべての新機能とバグ修正にはテストを付随させなければならない。テストは実装開始前に記述され、テストの正当性を検証するために最初は失敗しなければならない。

**遵守必須ルール**:
- テスト記述 → テスト失敗 → 機能実装 → テスト成功
- APIエンドポイントにはpytest-asyncioを使用した統合テストが必須
- フロントエンドコンポーネントにはJest/React Testing Libraryテストが必須
- エージェントロジックの変更には、モック化されたLLM呼び出しを含むユニットテストが必須
- テストカバレッジは新しい変更により低下させてはならない

**根拠**: FastAPIとLangGraphの非同期特性により、バグは微妙で発見が困難になる。テストファースト開発により、非同期動作、データベースインタラクション、エージェントワークフローがデプロイ前に検証される。

### III. 非同期ファーストの実装

すべてのI/O操作はasync/awaitパターンを使用しなければならない。データベースクエリはasyncpgドライバーを使用したSQLAlchemy 2.0非同期エンジンを使用しなければならない。APIエンドポイントは非同期関数でなければならない。バックグラウンドタスクはメインイベントループをブロックしてはならない。

**遵守必須ルール**:
- すべてのデータベース操作に`async def`を使用する
- すべてのI/O操作（DBクエリ、HTTPリクエスト、LLM呼び出し）に`await`を使用する
- 長時間実行されるエージェントワークフローにはFastAPI BackgroundTasksを使用する
- 非同期コンテキストで同期ブロッキング呼び出しを絶対に使用しない
- データベースセッションはSQLAlchemy 2.0の`AsyncSession`を使用しなければならない

**根拠**: Ghost-Squadは、数秒かかる可能性のあるLLM呼び出しを伴う複数のミッションを同時に処理する。非同期ファーストにより、エージェントワークフローの実行中もAPIの応答性が維持される。同期と非同期のコードを混在させると、デッドロックとパフォーマンスの低下につながる。

### IV. 段階的な機能強化

機能は段階的に提供され、各段階で独立した価値を提供しなければならない。複雑な機能は、洗練を加える前に、エンドツーエンドで動作するシンプルな実装から始めなければならない。システムはすべての段階で機能的でなければならない。

**遵守必須ルール**:
- 機能を追加する前にエンドツーエンドの機能を実装する
- 各ユーザーストーリーは独立してテスト・デプロイ可能でなければならない
- リアルタイム機能はWebSocket移行前にポーリングから始める
- エージェントのワーカーは複雑なロジックを実装する前にシミュレートする
- スキーマ変更は可能な限り後方互換性を維持しなければならない

**根拠**: TODO.mdは複数の部分的に実装された機能（ワーカーシミュレーション、WebSocketの代わりのポーリング）を示している。段階的な機能強化により、開発中にシステムを安定させながら、早期に価値を実証できる。

### V. セキュリティと設定管理

セキュリティに関わる情報をリポジトリにコミットしてはならない。認証と認可は本番デプロイ前に実装しなければならない。設定は環境変数に外部化しなければならない。

**遵守必須ルール**:
- APIキー、パスワード、シークレットは.envファイルに配置（docker-compose.ymlではない）
- .envファイルは.gitignoreに含めなければならない
- APIエンドポイントは本番環境前に認証/認可を実装しなければならない
- CORS originsは環境変数で設定可能でなければならない
- データベース認証情報は環境変数を使用しなければならない
- OPENAI_API_KEYは.envから読み込み、絶対にハードコードしない

**根拠**: 現在のコードベースにはTODO.mdで指摘されたセキュリティ問題（ハードコードされたシークレット、認証なし）がある。この原則により、セキュリティ脆弱性のコミットを防ぎ、安全な本番デプロイを保証する。

## 品質とパフォーマンス基準

### コード品質要件

- **Pythonコード**: Blackフォーマット（行長88）、Isortによるインポート整理、Flake8リントをゼロ警告で通過しなければならない
- **TypeScriptコード**: Next.jsルール付きESLintを通過しなければならない。strictモードを有効にすべき（現在は無効だが改善目標）
- **日本語コメント**: Ghost-Squad固有の概念やドメインロジックの説明に許可され、推奨される
- **エラーハンドリング**: LLM API呼び出しには、フォールバック動作または意味のあるエラーレスポンスを含むtry/exceptを含めなければならない

### パフォーマンス基準

- **APIレスポンスタイム**: ミッション作成はバックグラウンドタスク開始と共に即座に返却しなければならない（ノンブロッキング）
- **フロントエンド更新**: ポーリング間隔は2秒であるべき（現状）だが、不要な再レンダリングを引き起こしてはならない（スマート更新検出を使用）
- **データベースクエリ**: N+1クエリを避けるため、mission+tasksリレーションシップにイーガーローディングを使用しなければならない
- **エージェント実行**: ワーカーノードは観測性のためにエネルギーコスト（LLMトークン使用量）を追跡・報告しなければならない

### テスト基準

- **テスト実行**: `make test`はAPI（pytest）とWeb（Jest）の両方で通過しなければならない
- **テスト環境**: APIテストはaiosqliteドライバーを使用したインメモリSQLiteを使用しなければならない
- **テスト分離**: テストは外部サービスに依存してはならない（LLM呼び出し、外部APIにモックを使用）
- **テストカバレッジ**: エージェントロジック、APIエンドポイント、UIコンポーネントにテストが必須

## 開発ワークフロー

### ブランチとコミット

- フィーチャーブランチは`feature/###-descriptive-name`パターンに従わなければならない
- コミットメッセージは説明的であり、該当する場合はissue番号を参照すべき
- データベーススキーマ変更は文書化され、開発には`make db-reset`が必要

### コードレビュー要件

- すべての変更はコミット前に`make lint`を通過しなければならない
- すべての変更はマージ前に`make test`を通過しなければならない
- セキュリティ関連の変更（認証、シークレット管理）は原則Vへの準拠を明示的にレビューしなければならない
- エージェントロジックの変更にはLLMの動作とフォールバック処理の説明を含めなければならない

### 開発環境

- **推奨セットアップ**: すべてのサービス（API、Web、DB、Redis）に`docker-compose up`を使用
- **テスト**: `make test`ですべてのテストスイートを実行
- **コード品質**: コミット前に`make format`と`make lint`を実行
- **データベース管理**: モデル変更後のスキーマ再作成に`make db-reset`を使用
- **ローカル開発**: 可能だがPostgreSQL 15とRedisをローカルで実行する必要がある

### 技術スタック制約

- **バックエンド**: Python 3.11+、FastAPI、SQLAlchemy 2.0、LangGraph、OpenAI SDK
- **フロントエンド**: Next.js 14、React 18、TypeScript、Tailwind CSS、dnd-kit、Framer Motion
- **データベース**: PostgreSQL 15（本番）、SQLite + aiosqlite（テスト）
- **キャッシュ/キュー**: Redis 6+
- **CLI**: Go 1.21+、Bubble Tea TUIフレームワーク
- **インフラ**: ローカル開発にDocker Compose

## ガバナンス

### 憲章の権限

この憲章は、他のすべての開発プラクティスとガイドラインに優先する。この憲章と他のドキュメントとの間に矛盾が生じた場合、憲章が優先される。この憲章の変更には、文書化された根拠とプロジェクトメンテナーの承認が必要である。

### 改訂手続き

1. 具体的な文言変更と根拠を含む改訂案を提案
2. 既存コードとテンプレートへの影響を文書化
3. 影響を受けるすべてのテンプレート（plan-template.md、spec-template.md、tasks-template.md）を更新
4. セマンティックバージョニングに従ってバージョンを増分:
   - MAJOR: 原則の削除または後方互換性のないガバナンス変更
   - MINOR: 新しい原則またはセクションの追加
   - PATCH: 明確化、文言改善、非セマンティックな変更
5. LAST_AMENDED_DATEを改訂日に更新
6. 憲章の変更とテンプレート更新を含むプルリクエストを作成

### コンプライアンスとレビュー

- すべてのコードレビューはコア原則I-Vへの準拠を検証しなければならない
- セキュリティレビューは原則V（セキュリティと設定）を明示的にチェックしなければならない
- 機能仕様は該当する原則を参照しなければならない
- 実装計画には機能を原則にマッピングする「Constitution Check」セクションを含めなければならない
- 違反は「Complexity Tracking」テーブルで却下された代替案と共に正当化しなければならない
