# Gap Analysis: Importer機能

## 分析サマリー

### スコープ
外部データソース（メール等）から問い合わせを自動取り込みするImporter機能の実装ギャップ分析

### 主要な発見事項
- 既存のInquiry機能（Repository、Validator、API）は完全実装済みで、問い合わせ作成APIを直接利用可能
- StoryGenerationServiceのAI統合パターン（OpenAI、リトライ戦略、サニタイズ）を再利用可能
- プラグインアーキテクチャは新規作成が必要だが、Service層の分離パターンを踏襲可能
- 既存のエラーコード体系（GS-xxx）を拡張してImporter用コード範囲を定義可能

## 2. 実装アプローチオプション

### Option A: 既存コンポーネント拡張

**対象ファイル:**
- `api/services/story_generation_service.py` のAI統合パターンを参考に新規サービス作成
- `api/models/database/inquiry.py` の`inquiry_metadata`スキーマを拡張
- `api/config.py` に設定項目追加

**トレードオフ:**
- ✅ 既存パターンの即時活用
- ✅ 学習コスト低
- ❌ プラグインアーキテクチャの柔軟性が限定的
- ❌ 将来の拡張時にリファクタリング必要

### Option B: 新規コンポーネント作成（推奨）

**新規作成ファイル:**
```
api/
├── models/
│   ├── database/
│   │   └── import_record.py       # インポート記録モデル（将来用）
│   └── schemas/
│       └── importer.py            # Pydantic スキーマ
├── services/
│   ├── importer/
│   │   ├── __init__.py
│   │   ├── importer_service.py    # メインサービス
│   │   ├── analysis_service.py    # AI解析サービス
│   │   └── plugins/
│   │       ├── __init__.py
│   │       ├── base.py            # プラグイン基底クラス
│   │       ├── registry.py        # プラグイン管理
│   │       └── email_plugin.py    # メールプラグイン
└── routers/
    └── importer.py                # APIエンドポイント
```

**トレードオフ:**
- ✅ 明確な責務分離
- ✅ プラグイン拡張が容易
- ✅ 独立したテストが可能
- ❌ 初期開発コストが若干高い
- ❌ ファイル数増加

### Option C: ハイブリッドアプローチ

**フェーズ1（MVP）:**
- メールプラグインのみ実装
- 最小限のサービス構造

**フェーズ2（拡張）:**
- プラグインレジストリの完全実装
- 他データソース対応

**トレードオフ:**
- ✅ 段階的なリスク軽減
- ✅ 早期フィードバック取得可能
- ❌ フェーズ間の整合性管理が必要

## 3. 技術的考慮事項

### 再利用可能なパターン

| パターン | ソースファイル | 適用先 |
|---------|--------------|-------|
| リトライ戦略（指数バックオフ） | `story_generation_service.py:88-120` | メール接続、AI呼び出し |
| OpenAI API統合 | `story_generation_service.py:140-200` | AI解析サービス |
| 入力サニタイズ | `story_generation_service.py:60-85` | メール本文処理 |
| ValidationResult/Error | `inquiry_validator.py:15-30` | Importer バリデーション |
| エラーコード体系 | `GS-001`～`GS-204` | `GS-301`～で拡張 |
| Repository CRUD | `inquiry_repository.py` | 問い合わせ作成時に利用 |

### 新規依存関係

| ライブラリ | 用途 | 備考 |
|-----------|-----|------|
| `imaplib` | IMAP接続 | Python標準ライブラリ |
| `email` | メールパース | Python標準ライブラリ |
| `poplib` | POP3接続（オプション） | Python標準ライブラリ |

### 推奨エラーコード範囲

| コード | 説明 |
|-------|-----|
| `GS-301` | プラグイン未検出 |
| `GS-302` | プラグイン初期化失敗 |
| `GS-303` | データソース接続失敗 |
| `GS-304` | AI解析失敗 |
| `GS-305` | 重複インポート検出 |
| `GS-306` | メール取得失敗 |
| `GS-307` | リトライ上限超過 |

### inquiry_metadata 拡張スキーマ

```python
{
    "importer": {
        "source_type": "email",           # データソース種別
        "source_id": "message-id-xxx",    # 外部システムID
        "imported_at": "2026-01-11T...",  # インポート日時
        "confidence_score": 0.85,         # AI解析信頼度
        "needs_review": false,            # レビュー必要フラグ
        "original_subject": "...",        # 元のメール件名
        "original_sender": "..."          # 元の送信者
    }
}
```

## 4. 工数・リスク評価

### 工数見積

| 要件 | 工数 | 根拠 |
|-----|------|-----|
| Req 1: プラグインアーキテクチャ | **M** (3-5日) | 新規パターン、既存サービス参考可能 |
| Req 2: メールプラグイン | **M** (3-5日) | 標準ライブラリ使用、リトライパターン再利用 |
| Req 3: AI解析 | **S** (1-3日) | 既存AI統合パターンの応用 |
| Req 4: 問い合わせ生成 | **S** (1-2日) | 既存Repository直接利用 |
| Req 5: エラーハンドリング | **S** (1-2日) | 既存パターン再利用 |
| **合計** | **L** (1-2週間) | 新規コンポーネント + 統合テスト |

### リスク評価

| リスク要因 | レベル | 軽減策 |
|-----------|-------|-------|
| プラグインアーキテクチャ設計 | **Medium** | 既存Service層パターンを踏襲 |
| メールサーバー接続安定性 | **Medium** | リトライ戦略、接続プール |
| AI解析精度 | **Low** | 既存パターン活用、プロンプト調整 |
| 既存Inquiry APIとの統合 | **Low** | 完全実装済みのAPIを利用 |

## 6. 設計フェーズへの推奨事項

### 推奨アプローチ: Option B（新規コンポーネント作成）

**理由:**
- プラグインアーキテクチャの要件に最も適合
- 将来の拡張（Sentry、Slack等）を考慮
- 既存コードへの影響を最小化

### 設計フェーズでの重点項目

1. **プラグインインターフェース設計**
   - `PluginBase` 抽象クラスの定義
   - `fetch()`, `parse()`, `validate()` メソッド規約

2. **AI解析プロンプト設計**
   - 問い合わせタイトル・本文生成
   - 優先度・カテゴリ推定
   - 信頼度スコア算出

3. **エラーハンドリングフロー**
   - リトライ対象エラーの分類
   - 手動リトライAPIの設計

4. **テスト戦略**
   - メールサーバーモック
   - OpenAI APIモック
   - E2E統合テスト
